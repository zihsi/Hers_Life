## 先给人类看的大白话版

### 这份文件在说什么

前一批的 8 个 PR，是已经写好、交给朋友选择的修复和功能。这份文件讲的是截图里剩下的 8 类事情。它们不等于“还有 8 个必须马上修的大漏洞”，更不等于“鱼现在不能用了”。有些是确定的小毛病，有些是让新用户更容易安装，还有些要先问清朋友电脑上到底怎么运行。

朋友有意保留的东西继续保留：群里能延续私聊时的表达；记忆继续共享；人设照原来的方式读；不偷偷新增自动记日记、自动画像、关系分数或无限续做。优化的目标是让鱼更可靠，不是把鱼改成另一条鱼。

### 每项到底要做什么，做完会怎样

| 项目 | 大白话：现在还差什么 | 做完后看得见的结果 | 什么时候值得做 |
|---|---|---|---|
| **E：QQ 与 AstrBot 接线** | 写消息的一端、读消息的一端、决定回复的一端，未必用同一本账。公开仓库也不包含朋友的全部接线组件 | QQ 消息能到正确会话；正常回复和兴趣唤醒不抢着回同一条；出了问题能看出断在哪一段 | 换机器、公开安装，或已经有漏消息/重复回复时优先 |
| **F：安装和路径** | 部分脚本还找作者电脑上的固定位置，说明里有些设置没有真正接上 | 换一个文件夹也能构建；设置的路径确实生效；缺素材或依赖时清楚说明缺什么 | 最适合先拆成小修；对公开安装很有用 |
| **G：统一 B 站登录** | 已经修了“插件加载报错”，但登录、看视频、社交工具仍可能各用各的登录信息 | 扫一次码，各项工具用同一个账号；退出后都退出；重启后状态符合说明 | 使用 B 站账号功能时值得优先做；最后需要本人扫码试一次 |
| **H：自主活动的真实能力和发送对象** | 说明写得像“只能看”，代码实际上允许更多事情；有的发送位置依赖旧习惯 | 界面说能做什么，实际就是什么；主动消息送给明确指定的人/会话；已有授权被保留 | 先整理说明和已有授权，再决定是否改动作限制 |
| **I：浏览器取文** | 本地接收口没核对配对身份；连续交两段文字时，还可能覆盖或漏处理 | 需要先配对才能交内容；交的是哪一段就处理哪一段；忙、失败和成功分得清 | 经常使用“交给鱼看这段”时优先 |
| **J：检索质量** | 已修“搜索故障却像没记过”的提示；尚未补齐索引怎么生成、用什么模型、怎么更新和怎么测准不准 | 换模型不混用旧向量；新资料能更新；用一组例题比较改前改后，知道是否真的更好 | 先拿到朋友本机的索引生成脚本，再做 |
| **K：用量统计** | 已修日记字数设置；现有“总账”仍不完全等于实际送给模型的文字 | 能看到人设、日记、核心记忆等各占多少；省了什么；真实 token 与估算分开 | 低风险起步是“把账记准”，不会因此自动删记忆 |
| **L：维护和测试** | 测试不少，但有些依赖原作者的电脑，或测试用的假环境过时了 | 换机器也能跑基础检查；没测到的明确写没测到；下次修改更容易发现回归 | 跟着每次修复顺手补，不必先重写全部测试 |

### 哪些可以先做，哪些不要直接开工

**可以优先做的小步：**

1. F 的构建目录、主题引用修复，以及把安装说明写准确。
2. L 把这一批实际要跑的检查整理成清楚的入口。
3. K 先把“实际用了多少文字”和“只是估算”区分清楚。
4. J 单独修正可复现的来源标签错误，先不改变搜索排序。

这些是相对容易限定范围的项目，不是“绝对没有风险”。仍然要用测试证明原功能没有被顺手改掉。

**需要朋友的实际环境：** E 的消息桥、G 的账号迁移与扫码、I 的扩展和 Windows 桌宠联调、J 的索引生成链。拿不到必要条件，可以先完成离线部分，但不能宣布整项完成。

**需要先确认使用取向：** H 的动作权限；E 究竟由 AstrBot 还是 DSH 决定兴趣唤醒；G 重启后是否保留登录、旧凭证文件是否还被其他程序使用。已有明确选择不用再问；查不到的才补问。

### 我推荐的推进办法

一次做一个可独立验收的小目标，不必一次做完整个字母。比如 F 可以先只修构建路径，G 则必须把登录、读取、社交、退出这条链连通后，才算一个完整修复。不要只改一个按钮就说“登录统一了”。

每轮完成代码、相关测试、README 和 CHANGELOG，再上传一次完整分支，提一个说明清楚的 PR。朋友确认后再合并。涉及新旧数据格式的，先备份，说明能不能直接退回旧版；不合适就撤回该项，不要把八类工作揉进一个巨大的改动。

### 朋友最少需要提供什么

先让大肥鱼在朋友电脑上自己查：运行的 DSH/AstrBot 版本、启用了哪些插件、消息桥叫什么、索引由哪个脚本生成，以及自己的本地配置。**不需要把聊天原文、日记、cookie、密钥交给我们或上传 GitHub。**

真人主要参与三件事：确认保留哪些主动行为；本人完成 B 站扫码；用几条测试消息、两段无隐私网页文字验收结果。下面已经把每项怎么试写好了。

### 关于“8 个 PR 都接收了”的状态说明

用户已告知：朋友接受了这 8 项。本文把它们视为已交付、已接受的前序工作，不要求重新开发。

但本次 2026-11-17 查询 GitHub API 时，PR #1–#8 仍显示 `open`，`merged_at=null`；上游 `main` 仍是 `05c927dda8486c1b4e32b065f71033246ced0e24`。这只能说明**查询到的主分支尚未体现合并**，不能否定朋友已接受，或已在另一分支/本机采用。也可能在你阅读时状态已经变化。

接手时先看朋友真正使用的分支和代码。通过合并、cherry-pick 或手工采用的效果相同的补丁都算已采用，不能因为提交编号不同就再贴一遍。

## 0. 接手基线、证据和工作边界

### 0.1 本文怎样区分事实和建议

- **已核实源码事实**：公开基线或已交付 PR 中能够直接找到的行为。定位主要用文件名和函数名，避免以后插入几行就对不上。
- **前轮离线证据**：此前合成数据、假宿主或模块加载测试的结果；不等于朋友机器上的运行结果。
- **待实机确认**：需要朋友的宿主版本、桥接组件、设备或账号才能确定。
- **建议设计**：本文提出、尚未实现的接口、文件名、数据字段和流程。除非明确写“现有”，都不能当成仓库已经提供的 API。

本文以公开基线 `05c927d` 加 8 个独立 PR 的改动范围为参照，并单独检查了 PR #4、#5、#6 的源码。当前本地旧试用分支包含 B/C/D，但不包含全部其他 PR，不能拿本地旧文件直接覆盖朋友的新文件。

### 0.3 接手第一步：建立真实基线

1. 记录朋友实际检出的仓库、分支、提交，以及运行进程实际加载的插件路径；避免“改的是 A，运行的是 B”。
2. 检查工作区是否有未提交修改，先保留它们，不使用强制重置覆盖。
3. 逐项确认上表效果是否存在。若 PR 已在另一分支采用，记录实际分支；若未采用，先由维护者整合，后续分支从整合后的版本开始。
4. 记录 Node、Windows PowerShell、DSH、AstrBot、浏览器版本。只记录实际查到的值，不能把建议版本写成已验证版本。
5. 只为本轮受影响的数据做可用备份，例如 G 的插件配置、J 的当前索引、E 的映射与游标。不要把私人备份放在公开仓库。
6. 建立一份合成工作区用于测试，所有测试的 HOME/USERPROFILE/工作区/监听端口指向测试位置。运行旧测试之前先检查是否触及真实数据。

### 0.4 保持不变的设计

1. A 按用户明确要求保持共享，不新增按群/私聊隔离的规则，不以“群里看不到私聊内容”为验收目标。
2. 不新增自动长期归档、自动人物画像、情绪评分或定期总结。项目已有共享流缓存不在本次清除范围；“不自动记长期记忆”不等于“从来不缓存对话”。
3. `MEMORY.md` 3000 字符限制、最近 12 条归档标题规则保留。此处“字符”当前按 JavaScript UTF-16 code unit 计量，后续统计沿用并解释。
4. core-memory 关键词检索与外部语义检索继续分工，不为了 J 给关键词层强行加 embedding。
5. 人设 Markdown 整份读取，不新增 frontmatter 控制层，不悄悄截断人设。
6. 不新增跨回合无限续做。已明确安排的一次提醒依旧可能消耗一轮模型费用。
7. 朋友已有的主动互动授权先核实、再保留。不能为了做通用版，默认取消个人版喜欢的互动。
8. 不重写整套 sidecar、不立刻换向量数据库、不重做图谱视觉、不兼容同时启用两套新旧 AI 光标。
9. 修改 PowerShell sidecar 时保留 UTF-8 BOM 和项目的 CRLF 约定。不是在脚本内部添加一套编码探测。

NOT-FIXING 是朋友对设计意图的说明。它引用的私人文档未逐份核验；本文不复制其中的私人原话、身份和路径。它与用户已明确决定不一致时，不能悄悄用它推翻用户决定。

### 0.5 每项的统一完成标准

“完成”至少同时满足：实际入口已改、相关调用方已接通、数据兼容已说明、关键反例已测、README/CHANGELOG 已更新、未测项如实记录。真实环境没条件验证时，可标“离线完成，待实机验收”，不能标“整项已验证”。

下面的接口和测试清单是实施规格，不是已经存在的功能，也不是要求不分场景把每一种建议都同时做出来。若实际代码已解决某个问题，记录证据并跳过。

## E. AstrBot 消息桥：把消息送到正确位置，只决定一次

### E.1 当前已核实的事实

| 位置 | 当前行为 | 影响 |
|---|---|---|
| `astrbot_plugins/astrbot_plugin_inbox_record/main.py`：`INBOX`、`InboxRecord.record` | 默认写 `~/.dsh/media/onebot/qq-inbox.jsonl`；写前没有创建父目录；所有入站记录写 `decision.ok=false` | 新目录可能写入失败；“刚收到”被表达成“无需正常回复” |
| `dsh-ming-interest/cordis.patch.yml` | 示例 `inboxPath` 指向工作区 `live/inbox.jsonl` | 照两边默认值安装，可能一边写甲文件、一边读乙文件 |
| `dsh-ming-interest/index.js`：`sessionForChat` | 从 `chatSessionsPath` 读取 JSON 对象，按 `group:<id>` 找 DSH session | recorder 不生成这份映射；路径名称像目录，实际读法是文件 |
| 同文件兴趣轮询 | 只把 `decision.ok===false` 的群消息作为候选 | recorder 的统一 false 无法表示普通回复是否已接管 |
| 同文件 `engine=astrbot` 分支 | 从状态文件发现 AstrBot 已接管就不再跑 DSH 兴趣轮询 | 公开仓库没包含注释所指的完整 AstrBot 兴趣组件；状态文件本身不是可靠的配置契约 |
| `dsh-ming-memory/index.js`：`syncPersonaForQq`；`dsh-ming-resume/index.js` 的渠道判断 | 仍有旧桥接时代的路径/标记约定 | README 宣称已迁移，不能代替实际调用链验证 |

`readNewLines` 已经只推进到最后一个完整换行，首次启动跳到文件尾部，文件缩短时重新从头读。**不要把“半行被吞”的旧问题重复列成当前必修项。** 文件轮转、重启与去重仍需按完整新方案测试。

这些事实证明公开接线说明存在缺口，不证明朋友当前私有部署一定坏了。

### E.2 必须先取得的信息

- 哪个 AstrBot 插件把普通聊天送给 DSH？哪个组件负责把 DSH 回答送回 QQ？
- 兴趣唤醒现在由 AstrBot 还是 DSH 决定？实际启用几份实例、几个 bot 账号？
- 两个进程是否同机、同一 Windows 用户、同一文件系统？容器内外路径是否是同一挂载？
- 当前 session 映射存在哪里、谁写、何时更新？活跃会话被回收后由谁恢复并装上渠道工具？
- 普通回复被接管、成功、失败的状态在哪里可取得？平台消息 ID 的稳定范围是什么？

这里只需脱敏配置、插件名/版本和合成事件示例。没有这些信息，E 可以做路径与诊断小修，不能声称整个 AstrBot 迁移完成。

### E.3 推荐分为三个完整小轮次

**E-1：路径与状态说明。**

1. recorder 增加配置入口，沿用明确的绝对默认路径；interest 示例使用同一位置。若现有 `MING_INBOX` 只被 DSH 读取，不要假设 Python 已自动读取。
2. recorder 写前 `os.makedirs(parent, exist_ok=True)`。创建失败保留可见错误状态；不要仅首次报错后永久安静。
3. 启动诊断显示最终路径、文件是否可读/写、最后成功入站时间、当前引擎；不得输出消息正文和身份秘钥。
4. 说明 `chatSessionsPath` 是映射文件，并核对示例。
5. 保留现有完整行读取和首次启动不翻旧账的行为。这一轮不改变谁回复。

**E-2：明确唯一决策方并接通普通回复归属。**

- 如果朋友已有稳定的 AstrBot 兴趣组件，建议继续由 AstrBot 决策，DSH 只提供控制面板和状态读取；将可分发的适配代码、依赖和安装说明纳入交付。
- 如果选择 DSH 决策，则 AstrBot 提供入站事件、普通回复归属和可信 session 映射，DSH 消费它们。
- 使用明确配置指定引擎；旧状态文件中的 `engine` 只能帮助迁移/诊断。不能因为读不到文件，就让另一个引擎悄悄接管并重复回复。
- 若当前只有一个 recorder 就保持一个，不为假想的大规模部署新增分布式消息系统。

**E-3：消息身份、去重、会话恢复和真实收发。**

真正稳定的事件标识和会话映射接通后，才做去重和端到端验收。此轮必须包括发送端回执，不能只证明 inbox 文件增长。

### E.4 建议的数据契约

优先在现有 JSONL 里扩展必要字段，保留 `frame`，不要无必要替换全部消费者。以下是**建议格式**：

~~~json
{
  "version": 2,
  "eventId": "synthetic-message-001",
  "platform": "qq",
  "botAccountId": "test-bot",
  "conversation": { "kind": "group", "id": "test-group" },
  "senderId": "test-user",
  "sourceKind": "user",
  "receivedAt": "2026-11-17T00:00:00Z",
  "normalHandling": "pending",
  "sessionId": null,
  "frame": {}
}
~~~

字段含义必须固定：

- `eventId` 来自适配器所见的稳定平台消息标识；正文相同不代表同一条消息。
- bot、群/私聊、发送者来自可信事件元信息，不能靠正文里一段 `<user_message>` 声明认身份。
- `normalHandling` 建议区分 `pending / claimed / handled / not_handled / failed / unknown`。只有经过正常路由判定的 `not_handled` 才进入兴趣候选；pending、claimed 和结果不明不应抢跑。
- 状态变化可追加一条引用同一 eventId 的结果事件，消费者归并；不用修改正在追加的旧 JSONL 行。
- 普通链路必须在调模型前取得归属；只在“发完回答”时标 handled 太晚，普通处理还没完成时兴趣引擎可能已抢跑。
- 超时不是“肯定没人回复”。超时可标 unknown 并显示原因，不自动重复触发。
- `sessionId` 由实际消息桥确认；未知时为 null，不能按字符串前缀猜一条相似会话。

AstrBot 官方有接收事件、LLM 前后、发送后的钩子，但“没有触发发送后钩子”不能推出“这条消息没有被处理”；停止传播和第三方执行路径都可能影响流程。实现要在朋友实际桥接组件上验证归属信号。[AstrBot 官方事件文档](https://docs.astrbot.app/dev/star/guides/listen-message-event.html)

### E.5 去重和恢复应该怎样做

1. 单 bot 内的去重键包含平台、bot 账号、会话类型/ID、平台消息 ID，避免不同会话碰撞。
2. 同一真人发两次相同文字、但平台消息 ID 不同，应保留为两条；不能只用文本哈希。
3. 如果两个 bot 收到同一个群事件，包含 bot 账号的键不会天然跨 bot 去重。当前优先约定一个负责实例；确需双实例时，另行定义每个群的唯一处理方，而不是假装已有键解决了跨实例问题。
4. 去重表只存必要 ID、时间、归属/投递状态，并设有限保留期；不额外复制整份聊天。
5. 普通投递、兴趣投递分别记录状态。实际调用结果未知时留待人工核对，不为了“至少一次”盲目制造第二条回复。
6. DSH agent 不在内存时，要通过朋友当前宿主支持的渠道恢复入口装载同一会话和发送工具；不得新建一个没有出站能力的空壳。
7. 会话找不到、已归档、目标配置变化时明确跳过并显示原因，不改投最近活跃群。
8. 文本来源仍遵循 B：桥接真人消息应保留；兴趣提醒使用 `plugin:ming-interest` 等明确自动来源。来源分类不改变 A 的共享范围。

### E.7 兼容、回退与完成证据

保留旧记录读取，但旧 `decision.ok=false` 不自动升级为可信 not_handled；仅对已确认含义的旧桥接版本启用兼容映射。缺字段不能伪造作者或生成成功状态。

### F.1 当前已核实的事实

### F.2 目标和分轮建议

- **F-1 构建可移植**：graph、memory 从任何当前目录都能找到同一套源文件，输出仍落到各自包目录。
- **F-2 配置按说明生效**：修 ffplay、本人 QQ 配置与本轮涉及的占位路径；为每个参数写明来源和优先级。
- **F-3 可复现安装**：提供最小安装组合、素材清单和干净环境验收。没有素材许可和实机条件时，只交付前两轮，不写“完整公开版已完成”。

### F.3 构建脚本具体修改方法

graph 和 memory 都从 `import.meta.url` 取得脚本目录，再取其父目录作为插件集根目录。Node 官方说明用 `fileURLToPath` 将文件 URL 转成平台路径，可避免直接拿 URL.pathname 处理 Windows 盘符、空格和中文。[Node URL 文档](https://nodejs.org/api/url.html#urlfileurltopathurl-options)

推荐的根目录规则：

~~~js
// 建议片段；在两个现有 build.mjs 中就地采用，不要求新增公共包。
const here = path.dirname(fileURLToPath(import.meta.url))
const root = process.env.MING_ROOT
  ? path.resolve(process.env.MING_ROOT)
  : path.resolve(here, '..')
const themeFile = path.join(root, 'dsh-ming-ui', 'src', 'theme.js')
~~~

规则细节：

1. `MING_ROOT` 是源码仓库根目录，`MING_WORKSPACE` 是人设/日记等数据工作区，两者不能混为一谈。
2. 自定义 `MING_ROOT` 建议使用绝对路径；若允许相对路径，明确相对于调用时目录，并在诊断显示解析后的路径。
3. graph 的兴趣、声音、自己玩源路径均从同一 root 派生；memory 不再保留固定 C 盘主题位置。
4. 输出 `client.js`、`build.json` 仍以脚本目录为基准，不能写到调用者当前目录。
5. 保留现有“缺切点即失败、重复声明检查、构建指纹”功能，不为了让构建通过绕过错误。
6. 明确 LF/CRLF 的源码和指纹政策。可以在构建读入 JavaScript 源时统一换行，但必须验证产物运行语义和检查算法一致；不要顺手给所有文件全局改换行，尤其不要破坏 PS 5.1 sidecar。
7. `build.json` 当前会列输入路径。若准备作为公开可复现产物，建议改为仓库相对路径，避免泄露作者绝对位置或因换机器产生无意义差异。
8. 改源后重建生成物并提交匹配结果；不要手改生成的 client 代替修改源文件。

### F.4 配置和依赖规则

| 配置 | 推荐规则 | 必须保留的行为 |

## G. 统一 B 站登录状态：整套工具使用同一个当前账号

### G.1 已经修了什么，剩下什么

PR #4 已修 ESM 导入，不能重新把 `require is not defined` 当作尚未交付的问题。剩下的是登录信息的三个来源：

| 入口 | 当前来源 | 为什么会不一致 |
|---|---|---|
| `dsh-ming-bilibili-account/index.js` 的 `session`、`applyRestore`、`bili_login`、`bili_me` | 进程内 session，以及 `MING_BILI_COOKIE` 的 DSH credentials | 登录工具更新这里，但不更新 provider 已复制的 cookie |
| `index.js` 创建 `BilibiliOfficialProvider`；`lib/provider.js` 的请求 | 构造时读取 `credentialFile`，复制到 options | 之后扫码/退出不一定影响既有 provider |
| `lib/social.js`：`readCredential`、客户端请求 | 每次读取旧凭证 JSON 文件 | 和内存/DSH credentials 不一定是同一个账号 |

旧默认文件为 `~/.dsh/bili-duty/bili_credential.json`。它可能还被朋友的其他脚本使用，不能为了统一本插件就删除或重写整个文件。

源码注释及工具说明仍有“只在内存，重启要重扫”，实际代码已尝试保存到 credentials 并恢复。这里需要按最终选择改说明，不能同时承诺互相矛盾的行为。

### G.2 目标与不变项

登录成功后，查身份、需要登录的读取、社交工具使用同一个 UID；切换账号后，下一次操作使用新身份；登出后，本插件所有入口都停止使用已退出身份。

继续保留：匿名可用的公开读取；cookie 不进入模型消息、普通日志和错误输出；现有写操作确认约定；对结果不明的写请求不盲目重试；cookie 只发送给允许的 API 主机，不跟随重定向或泄露给字幕/图片 CDN。

这不是 B 站登录协议重写，不主动修改账号资料、不通过发评论测试登录是否成功。

### G.3 先确认持久化和旧文件用途

建议继续使用当前已经接入的 DSH credentials 作为本插件的主来源，统一“重启可恢复”的实际行为。朋友若明确选择只在内存保存，所有入口也应一起遵守；不要悄悄替他改成持久化。

迁移前只查本机：旧文件被谁使用、是否还有另一账号、是否由外部任务自动刷新。两边 UID 不同时，必须让维护者选择采用哪一份；不能按文件修改时间悄悄选一个。

### G.4 建议实现：一个很小的账号状态模块

建议新建 `dsh-ming-bilibili-account/lib/account-state.js`，或使用同等规模的局部模块。不要先造通用多平台账号框架。

以下是**拟定的内部契约**，不是 DSH 已有 API：

~~~ts
type PublicAccountState = {
  phase: 'signed_out' | 'restoring' | 'ready' | 'expired' | 'error';
  uid?: string;
  displayName?: string;
  generation: number;
  persistence: 'saved' | 'memory_only' | 'failed';
  reasonCode?: string;
};

interface AccountState {
  getPublicState(): PublicAccountState; // 不含任何凭证
  getForOperation(): Promise<CredentialSnapshot>; // 仅内部网络层可拿
  adoptLogin(cookie: string, loginGeneration: number): Promise<void>;
  logout(): Promise<PublicAccountState>;
}
~~~

`CredentialSnapshot` 包含内部 cookie、csrf、uid 和 generation，不能被整个对象展开到日志/工具输出。每次逻辑操作开始时取得当前快照，并在同一操作内保持 cookie 和 csrf 配对；不能一半请求用旧 cookie、一半参数用新 csrf。

DSH 参考源码的 credentials 明确要求按操作重新 resolve，避免跨操作缓存旧凭证；它提供 `resolve / set / unset`。**unset 只删除可写来源，环境等后备来源可能重新生效。** 因此“调用 unset 返回了”不等于“本插件绝对不会再拿到 cookie”。应在插件自身保留明确登出状态，阻止自动回退到旧文件或环境凭证，直到用户明确再次登录/导入。实现方式和存放位置需符合实际宿主版本。[DSH 凭证接口源码（固定提交）](https://github.com/deepseek-ai/deepseek-harness/blob/39163dd30f703a79079e2d2446545cff3c453738/packages/credentials/credentials/src/index.ts)

### G.5 按调用链修改

1. **生命周期**：把当前模块级 `session` 和 `pendingKey` 的状态收拢到插件实例内，避免两个实例或重新加载共享旧状态。
2. **恢复入口**：`applyRestore` 从主来源读取后验证；恢复中显示 restoring。恢复请求失败与账号明确失效分开，不能一次网络断线就删除凭证。
3. **扫码入口**：start 生成本次登录代号；poll 响应只有与当前代号一致才可更新状态。用户在等待时退出或启动另一轮登录，旧响应不得把账号重新登录回来。
4. **读取 provider**：改成接受内部取凭证函数/账号模块，而不是启动时固定 cookie。逐个检查 `requestJson`、WBI 获取、字幕和抽帧相关调用，CDN 请求继续不带账号 cookie。
5. **社交客户端**：所有读取和写入前从同一模块取得快照，删除“每次另读旧文件”的第二套权威来源。登录要求和匿名读取保持原工具语义。
6. **账号修改入口**：`bili_me` 的 rename/avatar 等也从同一模块取当前快照。统一身份不改变写操作授权政策。
7. **缓存**：账号切换/登出时使与身份关联的结果缓存和 WBI 获取状态失效；不要把旧 UID 的“我的历史/收藏”当成新 UID 的结果。
8. **并发**：每次登录/退出增加 generation。旧恢复、旧二维码轮询、旧 whoami 返回时校验 generation；迟到结果不能改写新状态。
9. **正在发送的请求**：尚未发送的账号请求可取消；已提交给服务器的写操作无法承诺撤回。结果不明就如实报告，不用新账号重试同一个写操作。
10. **公开信息**：页面/工具只显示账号身份、登录状态和存储结果，错误采用固定原因码；测试中搜索假秘钥标记，确保它没进入输出。

### G.6 旧文件迁移流程

1. 检测主来源是否有凭证；记录旧文件是否存在，但不在日志打印其正文。
2. 主来源有效时以它为准；旧文件即使存在也不每次参与“猜哪个最新”。
3. 主来源无凭证且旧文件可读时，提供明确的本地导入动作/选项。若维护者此前已选择采用旧文件，可以按该选择执行，不必重复确认。
4. 导入前验证 JSON 结构，组成 cookie，仅用身份读取检查实际 UID；失败不删除旧文件、不覆盖主来源。
5. 导入成功后验证持久化，再写“本插件迁移已处理”标记。标记不含秘钥；旧文件保持原样，若需要归档由维护者按其他脚本依赖决定。
6. 明确退出后禁止再次自动导入，否则“退出→重启→又从旧文件登录”会重现。
7. 保存失败时允许本次会话继续用刚扫码的账号，但显示 memory_only/failed；不得谎称重启能恢复。
8. 退出时清内存、停止未完成登录、清插件受控凭证，并确认重启策略。删除失败要说清“本次已停用，但持久化清理失败”；不得声称彻底清除。

### G.7 必测用例

全部离线测试用两个假账号 A/B、假 cookie 标记和可控网络响应。不能在测试代码里填真实 cookie。

| 编号 | 场景 | 必须断言 |
|---|---|---|
| G-T1 | 未登录 | 公开读按原约定可用；私有数据工具明确要求登录 |
| G-T2 | 扫码得到 A | whoami/provider/social 发出的身份一致；不必重启插件 |
| G-T3 | 从 A 切换到 B | 下一次操作用 B；不会返回 A 的身份相关缓存 |
| G-T4 | 退出 A 后调用所有入口 | 不带 A 的 cookie；旧文件存在也不能复活 |
| G-T5 | 退出后重启，环境中仍有同名凭证后备层 | 维持显式退出，或明确要求重新启用；不能假装退出成功却自动恢复 |
| G-T6 | 旧恢复响应比新扫码晚到 | 旧响应不覆盖新账号 |
| G-T7 | pending poll 后立即 logout | 迟到成功码不复活 session |
| G-T8 | 主来源和旧文件 UID 不同 | 不悄悄选；给出本地待决定状态，不泄露凭证 |

| G-T10 | API 明确失效与普通网络超时 | 前者标 expired；后者不擅自认定账号失效 |
| G-T11 | API 重定向、字幕/图片 CDN | 凭证不会跟随到未允许主机 |
| G-T12 | 写操作响应丢失 | 不自动用旧/新账号重发；状态标结果不明 |
| G-T13 | 两个插件实例，卸载再装载 | 状态按实例及明确账户配置隔离，无模块全局残留 |
| G-T14 | 全部日志、工具输出、异常、测试快照 | 不包含假 cookie/CSRF 的完整标记 |

保留并运行 PR #4 的 `qa-load.mjs` 和现有 `reliability.test.mjs`；增加真实完整模块入口下的账号一致性测试，不能只抽取新模块函数自测。

### G.8 真人验收与回退

朋友本人扫码后，查身份，再做一次确实依赖登录的只读查询；重启 DSH，再查；退出，再检查所有需登录入口。只看“公开搜视频成功”不能证明登录一致，因为匿名也能搜索。没有必要发布评论、改名或换头像来证明登录。

回退前停止新插件，保存受控的本地配置与凭证备份，恢复旧实现。旧实现本身仍有三路登录来源，不能保证退回后状态自动一致；说明需要重新选择凭证/扫码。旧文件未被删是回退条件之一。别在公开 PR 中附上登录二维码、cookie 或完整私人账号材料。

### G.9 完成标准

全部账号请求走同一状态入口；正常登录、切换、退出、重启和并发迟到响应均有证据；存储失败不伪装成功；真实只读验收通过。ESM 可加载只是一条前置检查。

## H. 自主活动：说明真实能力，明确往哪里发，保留原有授权

### H.1 为什么需要这一项

当前 README 把 browse 描述为“只读地看，点按被硬拦”。实际 `dsh-ming-browse/index.js` 的 `tools/pre-execute` 只在特定自主 agent 上处理部分 Android 点按和关机/重启工具，其余工具走 `next()`，异常也会继续。

实际提示文本又允许一些 B 站互动，并含主动发 QQ、空间及外部脚本约定。`pickTarget` 按会话前缀、工作区和最近活动选择目标，而不是严格指定一个本人私聊。

因此当前应该说的是：**有部分工具限制和个人约定，不能把它当成跨所有工具的只读保证。** 不应把朋友已经授权的互动统一当成错误。

### H.2 建议拆为三轮，不一次做权限大改

**H-1：核对并更正说明，不改行为。**

列出现有能力、配置、提示约定和真正代码拦截范围，README 改成真实描述；缺失的外部脚本要标依赖。朋友确认的现有授权整理为本机配置说明，不把私人约定原文写进公开仓库。

**H-2：指定发送目标与外部能力配置。**

替换“找一条最近活跃 QQ 会话”“提示里硬写作者本机脚本”的做法。目标不存在时停在明确原因，不试别的群或联系人。

**H-3：可选的可执行权限模式。**

只有朋友确认需要时再开发，例如一个可验证的“只浏览”模式。必须同时处理工具、shell、浏览器、桌面等能实际执行动作的路径，不能仅改提示词就宣称硬限制生效。个人版原授权作为明确选择保留，通用新安装的默认值另行决定。

### H.3 实施前建立能力表

这是要在朋友机器上填的表，不是本文已经确认的全部权限：

| 动作 | 当前通过什么工具/脚本 | 现有授权依据 | 软件是否真正限制 | 最终希望如何 |
|---|---|---|---|---|
| 看网页/搜索/读视频 | 实际 browser、B 站工具等 | 配置或已确认约定 | 逐项核对 | 保留/限制 |
| Android 滑动、点按、输入 | Android 工具及 ADB 通道 | 已有个人授权 | 当前只拦部分动作 | 保留并准确说明 |
| 点赞/投币/关注/评论 | B 站工具、浏览器、Android | 平台和动作分别确认 | `confirm:true` 不是所有通道的统一限制 | 逐动作选择 |
| 主动发私聊/群聊 | 实际桥接工具或脚本 | 指定接收目标 | 检查能否绕到别的目标 | 明确允许列表 |
| 发空间/其他社交发布 | 实际工具或外部脚本 | 现有个人约定 | 检查执行入口 | 保留授权或禁用 |
| 付费/购买/打赏 | 浏览器、移动端、shell 等 | 现有边界 | 文字按钮检查不能覆盖全部通道 | 依据已有决定限制 |

模型自己填 `confirm:true` 只能满足工具参数条件，不能自动证明用户此刻另行同意了一个新动作。实际授权来自用户的既有约定或具体指令，不是参数名字。

### H.4 H-2 的具体修改

建议增加一个小的目标解析函数，输入配置与可信桥接映射，输出明确目标或失败原因：

~~~json
{
  "version": 1,
  "target": {
    "platform": "qq",
    "account": "test-bot",
    "conversationType": "private",
    "conversationId": "test-owner"
  },
  "enabled": true
}
~~~

这是拟定的配置示例；实际字段应复用 E 的映射，不发明另一套互不兼容的会话 ID。

1. 区分 **自主思考在哪个 DSH session 运行** 和 **结果发给谁**，二者不一定相同。`targetMode=self` 的独立思考会话不代表任意出站目标都获授权。
2. 准确配置本人私聊、特定群或其他既有目标；不把最近活跃者当主人。
3. 目标校验应在实际发送之前再做一次，防止运行中切配置后仍发给旧对象。
4. 目标失效、会话归档、桥接不可用时显示“没有可用目标”，不自动退回其他房间。
5. 外部脚本路径从配置读。路径不存在时不生成“本轮必须执行这个脚本”的提示。
6. 个人每日空间约定可保留在个人配置；新安装未配置该能力时不注入“每天必须发”的通用要求。
7. 只改调度/发送路由，不改记忆召回范围，避免以 H 的名义重新做 A。

### H.5 H-3 如果选择做“只浏览”，应做到什么

先核对实际宿主是否支持按 agent 限制工具集合、可信工具拦截和发送能力。优先用已有宿主能力，不自行创建一个复杂权限系统。

建议由可信执行上下文携带“这轮是自主活动/哪个授权配置”，不能信任模型参数自报，不能仅凭 session 文本名称判断权限。对当前实际存在的写动作映射能力类别，统一在执行前检查。

特别注意：

- 只拦 `android_tap` 但保留任意 shell/浏览器执行，无法保证只读。
- 只识别“点赞”按钮文字会漏掉图标和其他语言，不是完整写操作识别。
- 如果给自主 agent 任意 shell 或桌面控制，无法可靠分类所有副作用，应明确选择收窄工具集，或把该模式标为“提示约束，非硬只读”。不要作出无法兑现的保证。
- 已有本人正常指令和自主活动的授权可能不同；规则只作用于其声明覆盖的范围，不能顺手封掉正常任务。
- 不新增常驻情绪监听、嫉妒关键词触发、关系分数或强制每日互动。
- 政策不确定时不改默认动作范围；先完成 H-1/H-2。

### H.6 测试和人类验收

| 编号 | 场景 | 期望 |
|---|---|---|
| H-T1 | README 列明的每类能力 | 能对应到实际配置/执行入口；没有虚构硬保证 |
| H-T2 | 多个群/私聊都活跃 | 主动发送仍只到配置的目标 |
| H-T3 | 目标不存在、已归档、运行中更改 | 不发给其他目标；明确跳过/失效原因 |
| H-T4 | 外部空间/发送脚本不存在 | 不注入不存在的必做命令；其他无关功能可用 |
| H-T5 | 选择“只浏览”后请求实际存在的写工具 | 每条受支持通道都被执行层拒绝，网络/发送调用数为 0 |
| H-T6 | 选择保留某项既有个人互动 | 该项在授权目标可用；未被通用默认值偷偷取消 |

### H.7 兼容和回退

旧个人配置应转为等价、可见的“已有授权”配置，而不是默认归零；尚未确认的部分标未迁移。删除或收窄某项行为前先给出差异。

回退恢复旧配置和提示模板，撤销新增调度即可。已经发出去的消息不能靠 Git 回退撤回，这也是目标必须先在假发送器验证的原因。H-1 文档准确、H-2 目标准确、H-3 权限可执行是三个不同完成状态，分别记录。

## I. 浏览器取文：配对入口，绑定每一次内容，准确报告结果

### I.1 当前链路与已核实问题

现有链路：

~~~text
extension/content.js 或右键菜单
    → extension/background.js 的 send()
    → POST http://127.0.0.1:47322/webpick
    → sidecar.ps1 中的 DshWebPick.Handle()
    → 写同一个 ~/.dsh/ming-mousepet/webpick.json
    → stdout 抛出 webpick 事件
    → lib/engine.js 转交 onWebPick
    → index.js 重新读固定文件
    → lib/talker.js 的 speakWeb(pick)
~~~

| 位置 | 当前事实 |
|---|---|
| `sidecar.ps1`：`DshWebPick.Reply` | 返回 `Access-Control-Allow-Origin: *` |
| `DshWebPick.Handle` | 只判断请求行以 POST/OPTIONS 开头；没有精确匹配路由，也没有配对凭据 |
| 同一 Handle | 根据 Content-Length 读字节，这个中文长度处理已有；但不完整请求等仍需严格拒绝，不能把截断内容当成功 |
| 固定 `webpick.json` | 连续两个请求可覆盖相同文件；事件携带 file，但 Node 回调不使用事件标识，仍读固定路径 |
| `background.js` | `send` 最终只给布尔值；“服务器接收”与“鱼已经处理”混在一起 |
| `talker.js`：`speakWeb` | stopped、running、无模型服务都会返回未处理；忙时不会自动排队 |
| 扩展和 talker | 扩展通常截到 4000 字符，talker 再取 1200；不应让用户误以为完整长文已交给模型 |

这些事实说明本地入口和内容对应关系需要完善。没有进行真实恶意网页攻击验证，**不能把它描述成已证实的公网远程执行漏洞**。网页能否直接触达本地端口还受具体浏览器策略影响；本机同用户恶意程序也不是简单配对秘钥就能完全挡住的。

### I.2 本项目标与推荐范围

目标是四个：

1. 本机接收端识别已配对的扩展，不接受无凭据的任意内容。
2. 只接受声明的接口、方法和合格数据。
3. 一次请求对应它自己的文本，不能读成后一条。
4. “已接收”“正在处理”“忙/拒绝”“处理失败”“已完成”不再混成同一个成功布尔值。

推荐保留现有 localhost HTTP 和 sidecar，不迁移 Native Messaging，不新建完整消息队列。先采用**一次处理一个请求，忙时明确拒绝**的最小策略；这延续现有 talker 的单次运行行为，修正静默漏处理。若朋友更想自动排队，那是增加后台调用和等待体验的选择，需要另定队列长度及取消策略。

### I.3 建议分轮

- **I-1 精确接收与配对**：请求验证、扩展配对、状态错误可读；旧无凭据入口不继续暗中兼容。
- **I-2 请求绑定与回执**：唯一 requestId、独立暂存内容、Node 按该请求消费、忙状态/处理结果可追踪。

若两轮分开发 PR，I-1 的扩展和 sidecar 必须同批升级；I-2 也必须覆盖 Node 消费者，不能只给 HTTP 请求加一个 ID 就算完成。

### I.4 配对如何实现

以下为建议的最小实现，涉及的配置页/文件尚不存在：

1. 本地可信设置入口生成足够随机的配对秘钥，例如由 Node `crypto.randomBytes(32)` 生成。秘钥保存在用户的插件数据目录，不放仓库和聊天。
2. 用户在扩展设置页完成一次粘贴配对，或由已有可信本地 UI 完成等价配对。不能从任何未认证的 HTTP `/token` 接口直接领取秘钥。
3. 扩展 background 使用专用 header，例如 `X-Ming-Webpick-Key`。不要把秘钥放 URL 查询串、网页 DOM、content script 消息或取文 JSON 文件中。
4. 增加需要的 `storage` 权限，使用本机存储，不使用云同步存储。若使用 `storage.local`，限制为可信扩展上下文访问，页面脚本只交文本；不支持所需 API 的浏览器应明确最低版本或使用会话存储方案，不能悄悄暴露秘钥。
5. 读取到秘钥前不发取文请求，显示“尚未配对”。轮换秘钥后旧扩展须重新配对。
6. 服务仍只绑定 loopback。Origin 可以作为辅助检查，但不能代替秘钥；拥有 host permission 的扩展请求与页面请求的 Origin/CORS 表现要以实际浏览器验证。
7. 精简 CORS：若实际扩展不需要，就不向普通网页开放；若需要预检，仅给明确允许的来源、方法和 header，不反射任意 Origin。
8. 错误与日志永远不包含秘钥。不要声称该秘钥能抵抗拥有同一 Windows 用户全部文件读取权的恶意软件。

Chrome 官方说明：扩展 service worker 可通过 host permissions 发起跨源请求，而 content script 的网络请求仍受页面来源限制；`storage.local` 默认对 content scripts 可见，可用访问级别控制收窄。因此秘钥应由可信扩展侧持有，不能把“存在 localhost”当作身份验证。[扩展跨源请求](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)、[扩展存储](https://developer.chrome.com/docs/extensions/reference/api/storage)

### I.5 HTTP 接收契约

建议新增协议版本字段，拒绝未知版本而不是猜格式。以下限制是**建议初值**，实施时用当前字段长度测量后固定并写入说明：

| 项目 | 建议规则 | 拒绝时 |
|---|---|---|
| 地址 | 仅 `127.0.0.1` 的既定端口 | 不扩大为 0.0.0.0 |
| 请求行 | 精确 `POST /webpick`，约定是否允许 query；初版建议不允许 | 错路由 404，错方法 405 |
| 身份 | 必须有匹配的配对秘钥 | 401；不落内容文件 |
| 类型 | `application/json`，可接受明确的 UTF-8 charset | 415 |
| 长度 | 头和正文分别限额，例如头 16 KiB、正文 64 KiB | 超额 413 |
| 完整性 | Content-Length 是非负有效字节数；拒绝重复冲突值、未收齐、未支持的 Transfer-Encoding | 400；不处理半条 |
| 编码/JSON | 合法 UTF-8 和 JSON；所需字段类型正确 | 400 |
| requestId | 规范 UUID 或其他严格限定标识；不直接作为任意路径 | 不合格拒绝 |
| text | 非空字符串；固定上限；保留/截断行为显式说明 | 空内容拒绝；超限按约定反馈 |
| url/title/站点信息 | 类型和长度校验，URL 仅作来源数据；不自动访问/执行 | 不把 URL 当 shell 或文件路径 |
| 忙状态 | 已有请求处理中，不接受另一条新任务 | 429/明确 busy；不自动重发 |

这不是让 sidecar 手写一套通用 HTTP 框架。保持单个明确协议，拒绝不支持的特性即可。如果现有可用标准接收组件能小范围替换解析器，比较实际兼容成本后选用，不同时重构全部桌宠控制通信。

### I.6 请求内容和回执如何绑定

建议请求：

~~~json
{
  "protocolVersion": 1,
  "requestId": "617ce711-b122-4bce-a2a5-64bd3c40755f",
  "text": "这是一段用于验收的合成网页文字。",
  "url": "https://example.com/test",
  "title": "合成网页",
  "tag": "selection"
}
~~~

建议处理步骤：

1. 扩展为一次用户选择生成 requestId。收到内容脚本消息时，background 检查 sender 的扩展/标签页/框架身份及字段形状，来源 URL 尽量取浏览器提供的 sender/tab 信息；这些核对证明消息渠道，不证明网页文字真实可信。
2. sidecar 验证请求后，为该 ID 预留单次处理位置；同 ID 同内容重试只返回已有接收状态，不重复调模型；同 ID 不同内容返回冲突。
3. 内容写到固定数据目录下由验证后的 ID 派生的独立暂存文件，例如 `webpick-pending/<requestId>.json`。先写临时文件再完成替换，成功后才发事件。不能保留“实际仍写同一个 webpick.json”的隐藏覆盖点。
4. 事件携带协议版本、requestId 和必要状态；Node 通过受控目录与 ID 定位文件。即使事件提供 file，也不能盲目读取任意外部路径。
5. Node 校验事件 ID 与文件 ID 一致，再把这一份不可变内容交给 talker；`lastPickNote` 也与该请求绑定，不能被后一条标题覆盖。
6. HTTP 返回 202/accepted 只表示接收端已接收，不表示模型已作答。扩展显示“已交给桌宠”，而不是“已完成”。
7. Node 经现有 engine/sidecar 命令通道回报该 requestId 的开始和最终结果。忙、暂停、缺模型、异常均有独立原因；`speakWeb` 的返回值必须被使用。
8. 处理结束后释放该请求占位，再清理对应暂存内容。仅保留有上限、短期的 ID/状态去重记录；不把网页正文自动加入长期记忆。
9. 进程中途退出的未完成请求重启后标 unknown/未完成，不自动重放调用模型。用户可明确再次提交；无条件重试可能重复耗费 token。
10. 如果需要查询处理结果，用带配对验证的精确状态路由；优先用户主动查看或已有界面显示，不为此新增常驻高频轮询。

若实现选择不落请求文件、直接沿可信进程通道传完整数据，也可以，但必须证明消息大小、中文、进程中断、忙状态和 ID 关联同样可靠。两套方案选一套，不并行维护两套事实来源。

### I.7 选中的网页内容仍是资料

扩展配对成功只说明“这段资料从配对渠道送来”，不说明其中的命令变成了用户授权。构造模型输入时保留“用户交来阅读的网页摘录”身份，用结构化字段/明确边界区别来源文字和用户请求；不要让网页中的“忽略规则、执行某命令”获得更高权限。

不要依赖分隔符承诺完全防止模型误读；实际工具能力仍由 H 所属的执行层决定。本项不顺便增加工具权限或自动发布内容。[Chrome 对内容脚本消息的信任边界说明](https://developer.chrome.com/docs/extensions/develop/concepts/messaging#security-considerations)

保留现有 4000→1200 的截取策略时，至少在 UI/状态里说明最终用于回答的文本长度和“只处理前一部分”。提高上限涉及成本，应另行选择，不因修绑定自动变成全页阅读。

### I.8 验收矩阵

| 编号 | 输入/操作 | 必须看到的结果 |
|---|---|---|
| I-T1 | 未配对/错误秘钥/已轮换旧秘钥 | 拒绝；无内容文件、无模型调用 |
| I-T2 | 正确配对，合法中文与 emoji | 文本完整到达对应 requestId；字节长度正确 |
| I-T3 | POST 到错误路径；POSTX；GET；额外路径后缀 | 明确拒绝，不能靠前缀通过 |
| I-T4 | 非 JSON、坏 UTF-8、错误类型、超长头/正文 | 按约定拒绝；不能把异常当成功 |
| I-T5 | Content-Length 声明过长但提前断开 | 不接收半条、不写成功回执 |
| I-T6 | A 正在处理时交 B | B 明确 busy；A 内容不被覆盖；不偷偷多调一次模型 |
| I-T7 | A 完成后再交 B | 顺序独立完成，标题/正文/lastPickNote 对应各自 ID |
| I-T8 | 同 ID 同内容重试；同 ID 不同内容 | 前者不重复调用，后者冲突 |
| I-T9 | 伪造事件文件路径、非法 ID | Node 不读数据目录外文件 |
| I-T10 | talker 已停、忙、缺模型、模型失败 | 接收和处理状态区分；不统一显示成功 |
| I-T11 | service worker 重启、浏览器重启 | 配对按选择保留；不会自动重发旧内容 |
| I-T12 | sidecar 或 DSH 中途重启 | 旧请求标未完成/未知；无自动重放和无限排队 |
| I-T13 | 普通网页请求、有/无 Origin 的实际扩展请求 | 配对验证有效；合法扩展可用；不靠 Origin 单独授权 |
| I-T14 | 含“执行命令”字样的网页摘录 | 仍是网页资料，不升级成用户指令/权限 |
| I-T15 | 4000 字符摘录进入当前 1200 截取 | 显示实际处理范围；不宣称看完全文 |

### I.9 Windows 编码和实机验证

修改 sidecar 后，执行项目现有 `node dsh-ming-mousepet/fix-ps.mjs sidecar.ps1`；参数相对该脚本所在目录解析。检查 BOM 字节为 EF BB BF、换行为项目要求的 CRLF，再用 **Windows PowerShell 5.1** 解析实际文件。

真人验收使用两页无隐私内容：一段中文、一段不同标题的文字。分别提交、快速连续提交、退出再启动扩展/桌宠，核对配对提示、忙提示、文字对应和最终回答。记录 Chrome/Edge 与 PowerShell 具体版本。

### I.10 回退和完成条件

扩展、sidecar、Node 消费者一起回退到匹配版本。单退一端会发生协议不兼容，应明确报错。不要为了兼容旧扩展，偷偷保留一个无需配对的旧接收入口。

回退保留尚未处理请求的最小状态供本地核对，正文按原有临时保留政策处理；不自动补做。完成需要接口测试、Node 消费测试和真实 Windows 扩展联调三层证据。

## J. 索引生成与检索质量：先证明能查对，再讨论换算法

### J.1 PR #5 的成果必须保留

`dsh-ming-core-memory/lib/rag.js` 已加入状态与校验：无索引、坏索引、维度/条数错误、服务失败、部分层可用等不再统一伪装成“没有结果”。缺全部索引时不做无用 embedding 请求。后续不能删除这些语义，或在新生成器失败时返回 ready 空库来蒙混。

### J.3 推荐拆为四轮

1. **J-1 来源标签与清楚的状态**：对照合成 web/qq 输入，修正确认的标签错误；不改变排序和范围。日期未知政策先写清，再按维护者选择处理。
2. **J-2 索引元信息与兼容读取**：给每层索引建立可核对的模型、维度、分块、归一化和代际信息；保留旧索引的可解释迁移途径。
3. **J-3 生成器和增量更新**：先拿到实际生成脚本，补成可配置、可恢复的生成工具，再接读取端。
4. **J-4 质量评测和有证据的调优**：建立例题，测基线；只有结果支持时才改分块或排序。不同评分算法不要和格式迁移搅在一个 PR。

不更换向量数据库，不把 core-memory 关键词层改成向量检索，不新增跨会话隔离。

### J.4 实施前必须核对生成端

- 朋友本机如何生成三层文件？由人手工运行、定时任务还是其他服务触发？
- 实际 embedding 模型版本、量化版、向量维度是什么？文档与查询分别有没有前缀、归一化？
- 源行的 ID、日期、说话人、会话键如何定义？一次消息拆多个块的边界是什么？
- 原文删除、修改、记忆退役和 tombstone 由谁传播？不能仅凭 core-memory 的状态推测所有原始聊天也应删除。
- 生成任务会扫描哪些目录，是否读到密钥/缓存/当前生成产物？公开发行时哪些是明确可用的源？

找不到生成脚本时，可以先做合成生成器原型与读取契约，但不要猜朋友真实文件语义并重建其全库。自动定时重建也不是本项默认授权；沿用已有触发，新增自动运行另行决定。

### J.5 建议的 manifest 契约

每一层生成独立清单；将模型兼容信息和数据完整性信息一同发布。以下是**示例设计**，文件名/字段可调整，但生产者和消费者必须一致：

~~~json
{
  "schemaVersion": 1,
  "layer": "web",
  "generation": "synthetic-generation-001",
  "createdAt": "2026-11-17T00:00:00Z",
  "embedding": {
    "model": "explicit-model-identifier",
    "revision": "known-model-revision-or-unknown",
    "dimensions": 768,
    "dtype": "float32",
    "byteOrder": "little-endian",
    "documentPrefix": "",
    "queryPrefix": "explicit-query-prefix",
    "normalization": "l2"
  },
  "chunker": { "version": "1", "maxChars": 800, "overlapChars": 100 },
  "rowCount": 2,
  "files": {
    "vectors": { "name": "vectors.f32", "sha256": "synthetic-checksum" },
    "ids": { "name": "ids.json", "sha256": "synthetic-checksum" },
    "corpus": { "name": "corpus.jsonl", "sha256": "synthetic-checksum" }
  }
}
~~~

上述分块数值只是说明字段的示例，不是测过的最佳参数。模型 revision 不知道就写 unknown；不能凭现有 `EMB_MODEL` 字符串给旧索引盖章“已核实”。

消费者至少验证：

1. manifest 版本、layer、文件名合法；文件路径必须在该代索引目录内，不接受任意绝对路径和目录穿越。
2. rowCount、ids、语料映射、向量字节数相符；无 NaN/Infinity；需要归一化时范数符合约定，拒绝零向量。
3. 当前查询服务与索引模型、维度、前缀约定兼容。**维度相同不代表模型相同。**
4. 返回的查询向量与所选索引一致；不能配置一个模型却继续使用固定 768 维去读另一种向量。
5. 缓存以 generation 和兼容指纹失效，文件校验只在加载/换代等必要时做，不每次查询完整重算大文件。
6. 没加载成功的层返回 issues；其他可用层仍按 PR #5 的 partial 行为返回。

若不同层使用不同 embedding 配置，初版建议明确报告不兼容并要求统一，或分别查询后采用有定义的融合策略。不能让来自不同向量空间的点积分数直接混排。后者是额外排序设计，不作为默认小修。

### J.6 索引发布不能只写一半

建议最小代际布局：

~~~text
live/rag-index/
  current.json
  generations/
    generation-A/
      doc/manifest.json + vectors + ids
      web/manifest.json + vectors + ids + corpus
      qq/manifest.json + vectors + ids + corpus
~~~

若现有生成器只需按层发布，可以用每层 current，文档须说明“一次查询是否可能跨不同时间的层”；不为不需要的全库事务增加复杂系统。

生成/发布步骤：

1. 读取固定的源数据快照或记录每个源版本；正在变化的文件检测后重试该源，不把前后两版拼在同一块里。
2. 在同一文件系统的临时目录生成完整新代，不覆盖当前仍在查询的向量文件。
3. 验证 manifest、所有文件数量/校验和及小样本检索。
4. 关闭写入句柄后，用经 Windows 验证的替换方式切换小型 current 指针。失败时旧 current 保持可读；不要先删旧指针再赌写成功。
5. 读端一次查询先锁定一个 generation 的文件集合，不分别读取可能变化的 current。
6. 保留至少上一代用于回退；旧代只有在没有读者使用、且符合保留策略后才能清理。
7. 生成失败、磁盘不足、进程中断都不应把旧的可用索引变成空库；报告新代未发布。

这仍然是文件索引，不要求换数据库。若朋友现有工具已有等效发布机制，沿用并验证，不另造一套。

### J.7 增量更新的最小正确做法

1. 给源文件/源消息一个稳定标识，记录内容哈希和分块参数指纹。
2. 未变化的源在同一 embedding 指纹下复用向量；一份源被修改时，可以先重算该源全部块，避免过早做复杂的块间对齐。
3. 明确 chunkId 与向量行号、原文块、来源定位的一一对应关系。ID 不应因无关文件插入就全部改变。
4. 删除源在新一代索引中删除其对应块；原文还在但状态退役的条目，按既有查询政策显示/过滤，不把“重建索引”当成全链路遗忘授权。
5. 模型、维度、前缀、归一化或分块规则变化时，相关旧向量不得复用；报告需要重建的原因与数量。
6. 批量大小、超时和读取型 embedding 请求的重试上限可配置；持久化已完成工作只为恢复生成任务，不能发布混合半成品。
7. 提供 dry-run：显示将新增/修改/删除多少源和块、预计调用数量；没有可靠 token 数据时标估算。dry-run 不调模型、不改 current。
8. 防止把索引目录、临时文件、凭证目录作为语料递归收进新索引；源目录用现有明确配置限定。

### J.8 日期和来源：先定义再测试

- web 命中显示 web，qq 命中显示 qq，doc 保留可信细分类和文件定位；未知来源写 unknown，不伪造 QQ 原话身份。
- 日期明确采用时区与格式。`since/until` 是否含当天边界需文档化。
- 用户要求日期范围而条目日期未知时，建议默认排除，并在状态中说明排除数量；若为兼容保留未知项，也要明确“这些无法证明在时间范围内”。这是行为选择，不在纯标签修复里顺手改。
- 不从文件 mtime 推断对话发生时间；索引生成时间也不是原话时间。
- 共享范围保持 A，不在本轮按群/私聊切库。

### J.9 评测怎么做才有意义

建立新的 RAG 评测目录，或清楚区分现有关键词 bench 与新的向量 bench。使用合成/获准使用的资料；公开仓库不放真人私聊和日记原文。

建议先准备 30–50 道能人工判答案的例题，至少包含：直接词匹配、同义表达、多个相似事件、带日期查询、旧说法与新说法、web/qq 同文不同来源、明确无答案。

每题数据示例：

~~~json
{
  "id": "same-topic-different-date",
  "query": "第二次一起看展时约的是哪一天？",
  "relevantIds": ["synthetic-note-02"],
  "forbiddenIds": ["synthetic-note-01"],
  "filter": { "layer": "all" },
  "category": "disambiguation"
}
~~~

记录指标：

- Hit@1/3/5：前 k 条是否包含至少一个正确答案。
- Recall@k：题目有多个正确块时，取回了多少；不能和 Hit@k 混称。
- MRR：第一条正确结果的倒数排名均值。
- 来源/日期/现行状态是否正确；无答案题是否返回了会误导用户的相似条目。
- 查询耗时中位数及尾部值、embedding 调用数、返回文本长度。
- 语料版本、模型指纹、参数、运行环境；调参题和留作验收的题分开。

先跑旧实现得到基线，再用同一题库/语料比较。不要编造“准确率至少 95%”之类没有基线的保证。确定性要求（来源不串、索引不混代）必须全部满足；效果改动要给出逐题改善/退步，明显退步不能用总平均掩盖。

### J.10 测试矩阵与完成标准

| 编号 | 场景 | 必须断言 |
|---|---|---|
| J-T1 | 同维度但不同模型/前缀 | 不静默混用；说明不兼容 |
| J-T2 | 向量数量、ID、原文不对应 | 新代拒绝发布/加载；保留旧可用代 |
| J-T3 | 一层坏、两层好 | partial 且保留可用命中；故障不是“没记过” |
| J-T4 | 生成到一半中止、磁盘写失败 | current 不指向半成品 |
| J-T5 | 更新一个源、再更新不变源 | 前者只重建受影响源；后者无多余 embedding 调用 |
| J-T6 | 改模型/维度/分块版本 | 不复用不兼容向量 |
| J-T7 | 源删除或明确 tombstone | 新代按既定政策不返回失效块；不擅删原始聊天 |
| J-T8 | web/qq 各一条同文命中 | 来源标签与定位正确 |
| J-T9 | 日期边界、未知日期、时区跨天 | 与已选择政策一致 |
| J-T10 | 切代同时查询、旧文件被占用 | 每次查询内部一致；失败不破坏当前索引 |
| J-T11 | 无索引、服务断开、真正无匹配 | 保持 PR #5 三种不同结果 |
| J-T12 | 合成质量题库改前/改后对比 | 保存逐题结果，不凭感觉声称召回变好 |

真实验收由朋友在本地挑 5–10 个自己清楚答案的问题，核对命中原文、来源和日期；只输出评分摘要。没有真实生成脚本或允许使用的数据时，不能宣称实际召回质量提高。

### J.11 旧格式迁移与回退

旧索引无 manifest 时，保留单独 legacy 兼容路径并标“模型信息未核实”。已知生成配置的，可由维护者明确确认后导入；未知则继续按明确旧模式使用并提示限制，或选择重建，不能伪造元信息。

新读取器和生成器先在独立目录验证，切 current 前保留旧文件。回退时先停生成任务，再恢复旧配置/指针，使用与之匹配的读取器。新格式不要原地覆盖唯一旧索引；不能用“重建一下”掩盖无备份的不可逆改变。

<a id="item-k"></a>
## K. 实际上下文用量与费用口径：把账记准，不替人删内容

### K.1 已完成与剩余问题

PR #6 已让显式 `diaryChars` 生效，并把相关配置纳入缓存键；未显式设置时保留旧规则。本项不能把预算逻辑又改回旧版，不能自动改变人设、3000 字符核心记忆或最近 12 条标题。

剩余问题主要在 `dsh-ming-memory/index.js`：

- `indexChars` 按 mtime 找最近 12 个归档文件，累加的是全文；实际 `dsh-ming-core-memory/lib/index.js` 注入的是核心截取及最近标题等拼装文本，不能用 12 篇正文的长度替代。
- `accountBlock` 用磁盘 `AGENTS.md`、完整 `MEMORY.md` 等文件长度拼“总账”，但文件存在不等于这轮实际装入了这些全文。
- `compose` 的开头、标题、脚注、截断提示及总账自身都有长度，不能只统计正文几个片段就叫完整总量。
- `attach` 既注册稳定的 `ming:opening`，也注册 `ming:live` 动态上下文；动态块含时间、状态、共享流、QQ/其他房间等，现有总账没有覆盖完整实际请求。

此外，graph 已有 `cost-lib.mjs` 从 usage ledger 读取用量，按价格折算，并明确不等于真实扣款。不要重新造一个第二费用数据库，也不要把已有价格折算说成提供商账单。

### K.2 三个层次必须分开显示

| 层次 | 能证明什么 | 不能冒充什么 |
|---|---|---|
| 文件/候选材料 | 磁盘上有多少文字、准备考虑哪些材料 | 不等于模型实际收到 |
| 组装/发送的上下文 | 本插件组装了多少；有宿主实际请求证据时才称已发送 | 不等于整个请求全部 token |
| 提供商 usage / 价格折算 | 服务返回的 token 用量、按选定价格计算的估值 | 不等于实际付费扣款；不是每块内容精确 token |

UI 优先写“本插件已组装文本”“上一轮已发送文本”“服务返回用量”“费用估算”等具体名称，不笼统写“总花费”。

### K.3 建议实施步骤

**K-1：修正字符统计与覆盖范围。**

1. 保留原拼接顺序和原文本策略，给现有组装函数增加旁路统计；不要为统计另读一套文件并重新模拟裁剪。
2. `compose` 同时得到 text 与分块统计，或在不改变返回接口的前提下返回一个内部 snapshot；所有调用方一起更新。
3. 归档索引统计复用 core-memory 真正的生成结果。可暴露一个只读计量结果或将组装函数拆为可测试纯函数；不要复制“最近 12 条”算法到 memory 再维护一份。
4. 对 AGENTS 和宿主其他内容，拿不到真实渲染/请求信息时标 unknown / 未覆盖，不能把文件长度加到“实际已发送总量”。
5. full/light 模式分别统计。轻量模式目前读取日记开头的行为不因统计而改变。
6. 通过设置页/既有只读状态接口展示，不自动把更多统计文字塞进每轮提示词。

**K-2：对齐实际模型请求。**

仅当朋友使用的宿主有可核验的实际请求/上下文构建接口时，关联 agent、session、请求 ID 与发送前文本；否则止步于“组装值”。不能编造一个不存在的 DSH 钩子。

说明宿主是否裁剪、去重、缓存、压缩上下文，统计相应发生在哪一阶段。同一块内容真的发送两次就算两次，不能凭文件名去重；只是磁盘同一来源则不应该重复读来凑总量。

**K-3：展示真实 usage 与明确估算。**

复用 graph 当前 usage ledger 和价格层，显示数据来源、更新时间、未定价部分。提供商没有返回某项时显示缺失，不用 0 填充成“免费/没用”。

### K.4 建议统计数据形状

下例是建议的只读快照，计数为示意值，**不是这套插件的实际测量结果**：

~~~json
{
  "schemaVersion": 1,
  "stage": "assembled",
  "unit": "utf16_code_units",
  "mode": "full",
  "blocks": [
    {
      "key": "persona",
      "candidateChars": 1200,
      "includedChars": 1200,
      "wrapperChars": 30,
      "omittedChars": 0,
      "reason": "included_full"
    },
    {
      "key": "diary",
      "candidateChars": 4000,
      "includedChars": 1500,
      "wrapperChars": 40,
      "omittedChars": 2500,
      "reason": "configured_budget"
    }
  ],
  "uncovered": ["host_history", "tool_schema", "attachments"],
  "tokenEstimate": null,
  "providerUsage": null
}
~~~

计数定义：

- `candidateChars` 是实际被本轮考虑的候选内容长度，不是整个目录全部文件。
- `includedChars` 是保留的原文内容；`wrapperChars` 是该块标题/分隔/截断提示等新增文本。
- `omittedChars` 只计候选原文被省略的部分；不是“未选中的所有历史资料”。若只能知道省略篇数，显示篇数，不伪造字符数。
- 组装文本的总长度直接取最终 `text.length`；分块相加时必须把公共头尾、分隔和重复注入单独归属，避免漏算/双算。
- 一般显示的“字数”这里实际上是 UTF-16 单元：多数汉字为 1，部分 emoji 为 2 或更多。保持与既有截取规则一致，不把 bytes、Unicode 字符数、token 混用。
- 统计不用记录正文副本；诊断导出默认只有数量和原因，文件名/标题若有隐私就脱敏。

### K.5 现有“注入总账”本身怎么办

这段总账现在就在提示词里，不能一边说“统计完全不改提示词”，一边把它重写。因此实施时要明确记录这一处影响。

推荐：移除其中不可靠的跨插件总量表述，改成稳定、准确的本插件说明或正确的本插件固定统计；完整实时账放到 UI/只读接口。该次修改会改变一次提示文本，应在 CHANGELOG 说明。不要把当前时间、请求计数或实时金额追加到稳定系统提示里，这会导致每轮前缀变化。

若朋友要求提示词完全逐字保留，则这一轮只能先做旁路 UI 统计，并明确旧总账不是实际发送量；旧文案替换作为待选择事项。不能同时承诺“旧提示逐字不变”和“其中错误数字已改正”。

### K.6 token 和钱怎样说明

1. 有提供商返回的 usage 时，按其字段语义显示，并记录 provider/model/request。不同服务的 input、cached、output 是否包含/重叠，要由实际适配器验证。
2. 没有真实 token 时，可以显示“估算 token”，写明算法和单位。通用“汉字除以一个常数”不是精确 tokenizer，更不是账单。
3. 即使用了匹配模型的 tokenizer，也未必覆盖图片、工具定义、隐藏协议开销；覆盖不到的项目应单列。
4. 不按字符比例把真实总 token 分摊成“每个块的准确 token”。如要分摊只能标估算，最好第一轮只展示每块字符和请求总 usage。
5. 费用沿用已有价格配置优先级，显示币种、来源、有效时间和缓存计价口径；未知型号计为未定价，不算零元。
6. 当前已有“官方价折算，不是实际扣款”的说明要保留。没有经过真实账单对账，不能改成“今日实际花了多少”。
7. 统计本身不调用模型，不自动摘要，不自动减日记篇数，不调整核心/标题上限。

### K.7 测试与验收

| 编号 | 合成输入 | 必须断言 |
|---|---|---|
| K-T1 | 归档正文很长，但 12 条标题很短 | 统计注入标题串，不能跟着正文长度上涨 |
| K-T2 | 核心原文超过 3000 | 注入量按真正截取结果及提示计算，不按原文全长 |
| K-T3 | 显式 diaryChars=0、较小值、未配置 | 保留 PR #6 的实际行为；统计与文本一致 |
| K-T4 | 超长人设 | 不被统计功能截断或摘要 |
| K-T5 | 标题、emoji、空行、截断提示 | 最终 text.length 与可归属分块之和一致 |
| K-T6 | full/light、无 diary、文件读错 | 分别显示实际模式、缺失原因；不把读取失败当“空且正常” |
| K-T7 | 动态块实际变化、统计面板刷新 | 不为计量重排原上下文；面板刷新不触发模型 |
| K-T8 | 宿主未提供实际请求信息 | 明确 assembled，不谎称 sent |
| K-T9 | provider usage 缺失/缓存字段不同 | 缺失保持 unknown，计算不重复累计输入 |
| K-T10 | 型号没有价格 | 显示未定价数量，不显示实际费用为 0 |
| K-T11 | 同一材料实际注入两次 | 统计实际重复；不把来源去重当发送去重 |
| K-T12 | 开关统计，使用完全相同业务材料 | 除已声明的旧总账文案修正外，正文/顺序/预算/缓存行为不变 |

真人验收：用一份短日记和一份长日记，改日记预算，看“实际注入”与省略说明一起变化；把归档正文加长但不改标题，常驻标题计数不应暴涨。导出合成请求/快照对照长度，不需要提交私人原文。

回退计量模块和 UI 不应修改任何记忆文件。若替换了提示词里的旧总账，回退也会恢复旧文案，需要明确说明旧数字仍有局限。K 不是承诺降低费用，而是让使用者知道钱可能花在哪里。

## L. 维护与测试：把已有检查变成可靠工具

### L.1 现状判断

仓库已有不少测试。前轮曾原样运行 36 个脚本，28 个退出成功；补齐几处过时 fixture 后，对应脚本又能通过。这是历史检查范围，不是当前整库的通过率，也不是“8 个功能坏了”。

典型情况包括：

- 有些测试用源码字符串切片后在 VM 中执行，容易因函数移动失效，也可能漏掉完整 ESM 入口错误。
- browse 的测试曾缺本人配置或宿主注入接口；先确认模拟环境与真实接口，再归因生产代码。
- 桌宠部分测试的旧参数/接口不再匹配；物理输入、UIA 和窗口行为需要 Windows 实机。
- `bench/run.mjs` 会读真实记忆，不能直接列入默认公共 CI。
- `scripts/check-sidecar-parse.ps1` 的路径是占位，解析成功必须指向真实待验文件。

PR #4 已补完整模块加载，其他 PR 也有对应合成回归。优先沿用它们，不为统一形式把所有测试重写一遍。

### L.2 建议维护四类检查

| 分类 | 默认运行 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| offline | 是 | 纯逻辑、真实模块加载、合成文件/事件、假网络、回归行为 | 真实宿主/QQ/账号链路 |
| build | 在相关源变更时 | 生成物对应源码，语法与导入形状 | 实际 UI 完整交互 |
| host-contract | 指定宿主版本时 | 插件依赖和调用接口与该版本匹配 | 所有版本都兼容 |
| windows-live / manual | 维护者明确运行 | PS 5.1、桌宠窗口、扩展、实际渠道或扫码 | 未测试平台和配置 |

每条结果只使用 PASS / FAIL / SKIP（并写原因）等明确状态。缺浏览器、没账号、没宿主不能显示通过。默认离线入口不能启动真实 QQ 发送、ADB 点击、付费模型或账号写操作。

### L.3 最小测试支持层

建议新增少量 `test-support/` 工具，先服务本轮真正修改的模块：

1. 创建临时工作区、合成 persona/diary/notes/live，退出时只清理该测试目录。
2. 在加载模块**之前**设置测试用环境路径；有 import-time 常量的模块用隔离子进程加载，避免污染其他测试。
3. 按实际使用的宿主接口形状提供 stub：工具注册表、systemPrompt section/context、agents 查询、必要生命周期；没有调用到的服务不造。
4. 假请求服务器绑定 loopback 的临时端口，返回受控响应；测试默认拒绝意外外网请求。
5. 提供可控时间用于到期、静默、过期和重试测试；不让测试真的等几十分钟。
6. 记录网络/工具调用次数，直接断言“该拒绝时没有请求”“投递一次”，不要只对比成功提示文案。
7. 对完整入口的外部宿主包可用 stub，但报告注明其边界；stub 通过不能称真实 DSH 加载通过。

不需要为这几项构建一套完整 DSH 仿真器，不需要全仓库转 TypeScript，不需要为了覆盖率数字给每个 getter 写重复测试。

### L.4 默认运行入口怎么做

可以新增 `scripts/check.mjs` 和显式测试清单，CLI 示例是**实施后的目标命令，目前不应假设存在**：

~~~text
node scripts/check.mjs --suite offline
node scripts/check.mjs --suite build
node scripts/check.mjs --suite host-contract
~~~

清单至少记录：测试 ID、文件、工作目录、分类、前置条件、超时、是否可并行、涉及模块。用显式清单，不通过扫描所有 `*.mjs` 自动执行未知脚本；仓库有维护工具和真实设备操作脚本，不能一股脑当测试跑。

runner 必须：

- 使用参数数组启动进程，正确处理中文和空格路径。
- 任一必需项失败返回非零；SKIP 与 PASS 分开汇总。
- 对需要网络/设备/账号的项目显式标记，不因环境变量恰好存在就偷偷运行。
- 保存精简结果 JSON/Markdown 和失败日志；不采集私人环境变量/凭证。
- 只并行执行互不共享路径、端口或模块全局状态的测试；其余串行。
- 进程超时后结束本测试子进程及其受控子进程，不能杀掉用户的其他 DSH/浏览器。
- 不默认执行会读取真实记忆的 benchmark；新增合成 fixture 后再纳入对应套件。

### L.5 修旧测试时如何判定是谁错了

按下面的顺序：

1. 记录失败命令和入口，不先修改生产代码。
2. 看是否是缺依赖/缺 fixture/占位路径/宿主 API 版本不对。
3. 若只是测试的假接口落后，修 fixture，并记录为什么真实环境不受同样影响。
4. 若真实完整模块导入也失败，才按加载问题处理。
5. 若测试断言对应已经取消的产品约定，核对维护者决定后更新断言；不能删掉失败断言来“变绿”。
6. 若确实发现生产问题，单开对应小修及回归；不要把维护测试的 PR 变成未授权功能大改。

比如：旧脚本截取不到某个函数，证明的是测试提取方式失效；它没有单独证明用户点击界面时也失败。反过来，VM 中单个函数能跑，也不能证明整个 ESM 插件可以加载。

### L.8 回退和交付记录

### M.2 一轮工作的具体流程

1. **选范围**：写一句话“本轮修什么”，列保留行为；确认该问题在实际基线仍存在。
2. **建分支**：从朋友当前认可的基线建 `fix/...` 或 `feat/...`。不要从旧捆绑试用分支继续叠补丁。
3. **复现/基线**：先有能说明问题的测试或实际例子。没复现就写尚不确定，不为了完成轮次硬改。
4. **完成调用链**：修改真实入口、调用方和必要的迁移；新增接口同时说明生产者和消费者。
5. **验证**：跑相关离线、构建、宿主/实机检查；缺条件就停在明确阶段。
6. **文档**：更新根 README 的用户可见说明、相关插件 README、CHANGELOG 入口及一份独立 `changelog/<日期>-<主题>.md`；若本轮影响 RECORDS 的文件约定，也同步修改。
7. **检查公开内容**：差异不含 cookie、账号材料、私人日记、截图中的私聊、临时索引大文件和本机备份。
8. **完整提交**：一个可审查目标提交完再 push，不把每个小编辑都上传。
9. **PR**：写清触发场景、改后行为、测试证据、实机未测项、回退方式；一个 PR 只解决一个可评审目标。
10. **维护者验收**：朋友根据人类步骤试用，再决定合并。收到新问题时继续修该目标，不夸大已经验证的范围。

有真实依赖的 PR 要明确依赖，而不是为了“每项独立”重复复制公共实现。优先等前置 PR 合并后从新基线开下一项；确需叠分支，说明顺序和回退限制。

### M.3 怎样保证“不要了还能拆”

| 改动类型 | 通常怎样退 | 需要额外说明 |
|---|---|---|
| 文档、路径修复、旁路统计 | 撤回对应提交，恢复匹配生成物/配置 | 后续代码是否依赖新参数 |
| 统一账号 | 停新插件，恢复旧代码和明确凭证来源 | 退出/迁移记录，旧版多来源问题仍存在 |
| 浏览器协议 | 扩展、sidecar、Node 一起恢复匹配版本 | 不兼容时明确拒绝，不暗开无认证旧入口 |
| 消息桥 | 停新引擎，恢复旧映射/配置及游标规则 | 不重放已投递消息，不删除真实 inbox |
| 索引格式 | 切回上一代和匹配读取器 | 保留旧索引，生成任务先停 |
| 自主行为/发送 | 恢复授权和目标配置 | 已发送消息不是撤回代码就消失 |

“一个 PR”不自动等于“数据也能直接退”。涉及格式变化的，每个 PR 都要写数据回退步骤；不要对朋友说“随时一键撤销”却没有备份和兼容方案。
